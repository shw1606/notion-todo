## 2026-11-11 — 순서와 섹션은 이 기기에만 둔다

**결정:** 목록에서 줄을 끌어 순서를 정하고, 레이블과 연한 배경색이 있는 섹션으로 묶을 수 있다. 이 배치는 Notion에
보내지 않고 App Group의 `layouts/<뷰 ID>.json`에만 둔다. (2026-11-09의 "리스트 순서 바꾸기는 하지 않는다"를 대신한다.)

- Notion API로는 뷰의 수동 정렬 순서를 쓸 수 없다. 그래서 순서를 Notion에 맞추려 하지 않고, 스티키 메모를 책상에
  늘어놓듯 이 기기에서 보는 배치로만 다룬다. 기기끼리는 맞추지 않고, 로그아웃하면 지워진다.
- 목록은 섹션 밖 항목 → 섹션 순으로 그린다. 새로 생긴 항목은 섹션 밖 맨 위에 온다. 순서를 정한 적이 없으면 Notion
  뷰의 정렬 그대로이고, `정리 ▸ Notion 순서로 되돌리기`로 돌아갈 수 있다(섹션은 남는다).
- 섹션은 이름(비워 두면 "새 섹션")과 색(6가지)만 가진다. 섹션에 속한 줄에 같은 색을 연하게 깔아 카드 한 장으로
  보이게 한다. 섹션 머리를 끌면 섹션이 담긴 항목과 함께 옮겨 가고, 섹션을 지우면 항목은 섹션 밖으로 나온다.
- 위젯과 메뉴 막대는 순서만 따르고 섹션은 그리지 않는다 (좁은 자리에 머리 줄을 넣지 않는다).
- 체크해서 뷰에서 빠진 항목의 자리는 50개까지 남겨 둔다. 체크를 되돌리면 제자리로 돌아온다.
- 저장은 "파일을 통째로 덮어쓰기"가 아니라 "저장된 배치에 변경을 적용"한다. 앱 창 여러 개와 위젯 확장이 같은 파일을 쓴다.
- SwiftUI `List`에서 확인하고 맞춘 것 (iOS 27.2 시뮬레이터):
  - 줄(문맥 메뉴 포함)에서 `model.layout`을 직접 읽으면, 끌어 놓는 순간 그 줄만 따로 다시 그려져 옮긴 줄이 제자리로
    돌아간다. 섹션 목록은 `body`에서 값으로 받아 줄에 넘긴다.
  - `moveDisabled`로 막은 줄의 자리에는 놓을 수도 없다. 그래서 줄을 모두 옮길 수 있게 두고, 빈 섹션은 안내 줄을
    따로 두지 않고 머리 줄이 놓을 자리를 겸한다.
  - 이미 그린 줄의 `listRowBackground`는 다시 읽지 않는다. 배경이 달라지는 줄(들어 있는 섹션·색·카드의 끝 줄)은
    줄 ID를 바꿔 새로 그리게 한다 (`LayoutRow.id`).
  - iOS의 섹션 머리에는 문맥 메뉴를 달지 않는다. 길게 눌러 끄는 동작과 겹쳐 끌다가 메뉴 항목이 골라졌다.
    같은 메뉴는 머리의 ••• 단추에 있다.

## 2026-11-11 — 메뉴 막대 아이콘은 숨길 수 있다

**결정:** Mac 설정에 "메뉴 막대" 묶음을 따로 두고 `메뉴 막대에 아이콘 표시`를 끄면 아이콘이 사라진다. 메뉴 막대 창의

- 전에는 같은 스위치가 "위젯" 묶음 안에 `메뉴 막대에 표시`라는 이름으로 있어서 찾기 어려웠다.
- 숨겨도 앱과 위젯은 그대로 동작한다. 다시 켜는 곳은 설정 한 곳이다.

## 2026-11-11 — 용량과 메모리: 기호를 떼고, HTTP 캐시를 끄고, 위젯을 덜 깨우고, 읽는 속성만 받는다

**결정:** Release 빌드는 기호 표를 떼어 내고(`DEPLOYMENT_POSTPROCESSING`·`STRIP_INSTALLED_PRODUCT`) 크기 우선(`-Osize`)으로
컴파일한다. 네트워크는 HTTP 캐시·쿠키가 없는 전용 세션(`URLSession.notion`)을 쓴다. 위젯은 보여 줄 내용이 달라졌을 때만
다시 그리게 한다. 쿼리는 페이지마다 앱이 읽는 속성(제목·완료·날짜)만 받는다.

- 용량 (서명한 Mac `.app` / 서명 전 iOS `.app`의 파일 크기 합, 2026-11-11): **Mac 11.1MB → 5.0MB, iOS 5.6MB → 2.6MB.**
  실행 파일이 번들의 98%였고 그 2/3가 기호 표였다. 아카이브가 아닌 Release 빌드(로컬 설치용)는 기호를 떼지 않고 있었다.
  기호는 dSYM에 남는다. `-Osize`는 앱 타깃과 패키지(`Package.swift`) 양쪽에 건다 — 패키지에는 프로젝트 설정이 닿지 않는다.
- 하지 않은 것: Mac의 Intel 조각을 빼면 절반이 더 줄지만 macOS 26이 Intel Mac을 지원해서 그대로 둔다. 앱과 위젯 확장이
  패키지를 각자 정적으로 품는 것도 그대로 둔다(공유 프레임워크로 묶는 이득이 작다). Swift 리플렉션 메타데이터는
  SwiftUI가 써서 끄지 않는다.
- `URLSession.shared`는 Notion 응답을 디스크 캐시(Cache.db)에 쌓고 있었다 — 실제 데이터 44KB에 캐시가 앱 4.2MB,
  위젯 확장 3.1MB. 받은 내용은 App Group 파일로 직접 캐시하므로 HTTP 캐시는 쓸모가 없다. 전용 세션으로 바꾸고,
  예전 캐시 파일은 실행할 때 지운다.
- 앱을 앞으로 가져올 때마다(새로고침) 위젯 타임라인을 다시 그리게 했고, 그때마다 위젯 확장이 떠서 Notion을 한 번 더
  조회했다. 이제 받아 온 목록이 화면에 있던 것과 다를 때만 다시 그리게 한다.
- 쿼리에 `filter_properties`를 붙여 제목·완료·날짜 속성만 받는다. 속성이 3개뿐인 "할 일 메모"에서는 응답이 8%만 줄지만
  속성이 많은 업무용 DB일수록 크게 준다 — 받아서 디코딩하는 양이 곧 위젯 확장(메모리 한도가 빠듯하다)의 순간 메모리다.
  없는 속성 ID를 주면 Notion이 400을 돌려주므로, 캐시한 뷰 정의가 낡아 400이 오면 뷰를 다시 읽고 한 번만 더 묻는다.
- 메모리 측정 (Mac, `vmmap`의 physical footprint, 2026-11-11). 줄어든 것과 늘어난 것을 같이 적는다.
  - 위젯 확장: 15.1MB → 11.1~12.8MB (두 번 잼). HTTP 캐시가 빠진 몫이다.
  - 디스크의 HTTP 캐시: 7.3MB → 0.
  - 앱(실행 15초 뒤, 5회): 38.4~38.8MB → 41.2~41.6MB. **약 2.7MB 늘었다.** 순서·섹션 화면(도구 막대 메뉴, 행마다의
    메뉴)이 SwiftUI 쪽에 만드는 몫이고(살아 있는 힙 14.3MB → 15.1MB, 나머지는 할당기·AttributeGraph 여유분), 앱이 직접
    잡는 데이터는 거의 없다. 메뉴 막대 아이콘을 숨기면 0.7MB쯤 준다.
  - 쓰는 동안 50~64MB 사이를 오르내리는 것은 이전 빌드도 같다. 시스템이 창 그림을 풀 때 잡는 1.6MB짜리 버퍼(CoreUI)와
    요청마다 잡는 1MB 버퍼(CFNetwork, 본문을 어떻게 보내든 같다)가 풀린 뒤에도 할당기에 남아 있는 것으로(뷰를 30번 연 뒤
    "Malloc Large (empty)" 7.9MB), 앱 코드에서 줄일 수 있는 부분이 아니다. 그동안 살아 있는 힙은 15.1MB → 15.4MB로
    거의 그대로다.

## 2026-11-09 — Notion 연결은 모든 워크스페이스용

**결정:** "Notion 연결하기"가 쓰는 OAuth 연결을 설치 범위 "모든 워크스페이스"(공개용)로 새로 만들고 client ID·secret을
바꾼다. 이름·아이콘·권한(이메일 제외)·리다이렉트 URI는 그대로다.

- 처음 만든 연결은 설치 범위가 개발 워크스페이스(Seo's Space) 하나였다. 그러면 다른 사람은 공식 빌드로 연결할 수
  없어서, 오픈소스로 내놓아도 직접 연결을 만들고 함수를 배포해야만 쓸 수 있었다.
- 설치 범위는 연결을 만든 뒤에 바꿀 수 없어서 새로 만들었다. 마켓플레이스에 올리지 않아도 모든 워크스페이스에서
  연결할 수 있다. 동의 화면에는 "Notion은 제3자 연결을 검토하지 않는다"는 안내가 붙는다.
- secret은 개발자 포털의 복사 버튼을 페이지 안에서 가로채 파일로만 옮겼다(화면 캡처·채팅·시스템 클립보드 없이).
  Vercel에는 sensitive로 넣고 다시 배포했다.
- 예전 연결로 받은 토큰은 새 client로 갱신되지 않는다고 보고, 이미 로그인한 앱은 한 번 다시 연결한다
  (로그아웃 → Notion 연결하기). 그다음 예전 연결을 지운다.

## 2026-11-09 — 앱에 보일 DB는 사용자가 고른다

**결정:** 사이드바·뷰 전환 메뉴·위젯 설정에는 연결이 볼 수 있는 DB 전부가 아니라 사용자가 고른 DB만 올린다.
온보딩에서 고른 DB 하나로 시작하고, `DB 추가…`로 더하고, 사이드바 문맥 메뉴나 설정에서 뺀다. 빼도 Notion은 그대로다.

- Notion 동의 화면에서 페이지를 고르면 그 아래 DB가 모두 연결에 공유된다. 그걸 다 올리니 할 일과 상관없는 DB가
  사이드바를 채웠다. 개인 액세스 토큰은 워크스페이스 전체가 보여서 "최근에 고친 30개"로 잘라야 했다(아래 결정을 대신한다).
- 고른 DB(data source ID)는 App Group의 `settings.json`에 둔다. 뷰 목록은 고른 DB만 다시 받아서 검색이 필요 없고,
  DB가 휴지통에 있거나 연결에서 빠지면(404) 고른 목록에서도 뺀다.
- 고르기 전 버전에서 올라오면 마지막으로 연 뷰의 DB 하나만 남긴다.
- 목록에서 뺀 DB의 뷰를 보여주던 위젯은 그대로 둔다. 위젯 설정 값은 캐시된 뷰 정의로도 찾는다.
- 고를 DB 목록(온보딩·`DB 추가`)은 검색 한 번으로 만들고 최근에 고친 30개까지 보여준다.

## 2026-11-09 — 앱 이름: Todo Widget for Notion

**결정:** App Store·Mac 앱·Notion 동의 화면의 이름은 `Todo Widget for Notion`, 홈 화면 이름은 `Todo Widget`
(한국어 기기는 `할 일 위젯`, `InfoPlist.xcstrings`).

- 노션 연동이 이름에서 바로 보이게 "… for Notion" 형식을 쓴다. App Store에 같은 형식이 많고(Widget for Notion 등),
  미국·한국 스토어에 같은 이름은 없었다. 노션 브랜드 가이드는 제품 이름에 "Notion"을 넣지 말라고 하므로 요청을 받으면 바꾼다.
- 이전 이름 "Notion Todo"는 "Notion"이 앞에 오고 스토어의 "NotionTodos"와도 비슷했다.
- 번들 ID·`notiontodo://`·저장소 이름 같은 내부 식별자는 그대로 둔다. 바꾸면 설치된 앱의 로그인과 위젯이 끊긴다.
- 함께 고친 것: 앱·위젯 타깃에 `GENERATE_INFOPLIST_FILE`이 없어서 `project.yml`의 `INFOPLIST_KEY_*`(표시 이름·실행 화면·
  iPad 여러 창·화면 방향·앱 카테고리)가 Info.plist에 하나도 들어가지 않고 있었다. iOS 전용 키는 `[sdk=iphone*]`로 묶었다.

## 2026-11-09 — 토큰 교환 함수는 Vercel에 둔다

**결정:** `auth/`를 Vercel(`https://notion-todo-auth.vercel.app`)에 배포한다. 코드는 플랫폼 중립인 `handle` 하나이고,
Vercel은 `api/index.ts` 어댑터로, Cloudflare Workers는 기본 export로 같은 코드를 쓴다.

- **모든 경로를 함수로.** `vercel.json`은 `rewrites`가 아니라 `routes`를 쓴다. 정적 출력이 없는 프로젝트는 올린 소스가
  정적 파일로도 나가고 `rewrites`는 그 뒤에 적용돼서, `/src/index.ts`가 그대로 보였다.
- **올리는 파일은 허용 목록.** `.vercelignore`가 `api/`·`src/`·설정 파일만 올린다. 로컬 비밀값(`.dev.vars`)이 섞이지 않는다.
- **사용자 정보 권한은 이메일 제외.** 앱은 사용자 ID·이름만 쓴다. 이메일까지 받으면 동의 화면에 "사용자와 이메일 보기"가
  붙어 첫 연결이 무거워진다.

## 2026-11-09 — 첫 연결은 버튼 한 번 (Widget for Notion처럼)

**결정:** 온보딩에서 키 발급·페이지 공유·페이지 고르기를 없앤다. "Notion 연결하기" → Notion 동의 화면에서
"액세스 허용" → 앱이 미리 골라 둔 출발점으로 "시작". 토큰 붙여넣기는 보조 경로로 둔다.

- **콜백은 앱 주소(`notiontodo://oauth`).** `auth/`의 `/callback`이 code·state를 그대로 넘긴다. HTTPS 콜백은
  Associated Domains·AASA 배포·서명 설정이 필요하고 브라우저마다 동작이 달랐다. 가로챈 code는 PKCE 검증 때문에 쓸 수 없다.
- **Mac은 Safari일 때만 인증 창.** 기본 브라우저가 Chrome 계열(시험한 ego lite 포함)이면 `ASWebAuthenticationSession`이
  같은 실행 안에서 두 번째부터 창을 띄우지 못하고 멈췄다(Apple 개발자 포럼 724366에도 같은 보고). 그래서 그 경우
  기본 브라우저 새 탭으로 열고, 브라우저가 앱 주소를 열면 마친다. 어느 쪽이든 기다리는 동안 취소할 수 있다.
- **새 메모 DB는 워크스페이스 맨 위에.** Notion API는 `parent: workspace`로 DB를 만들 수 있고(사용자의 "개인 페이지"),
  public integration 토큰으로 확인했다. 그래서 동의 화면에서 페이지를 고르지 않아도 된다. 맨 위에 만들 수 없는
  internal integration은 공유된 맨 위 페이지 아래에 만든다.
- **출발점은 앱이 고른다.** 이 앱이 만든 메모 DB가 보이면 그것, 아니면 새 메모 DB. 쓰던 DB(체크박스·status가 있는 것)는
  아래에 나열하고, 고르면 할 일을 보여주는 뷰를 자동으로 연다. 이 목록은 검색 한 번으로 만든다.
- **토큰은 개인 액세스 토큰을 권한다.** 사용자 권한을 그대로 써서 공유 단계가 없다(internal integration 토큰도 받는다).
  대신 워크스페이스 전체가 보이므로 뷰 목록은 최근에 고친 DB 30개까지, 3개씩 동시에 받는다.

## 2026-11-09 — 구현 중 확인한 사실로 정한 것들

- **기본 뷰는 "할 일을 보여주는 뷰".** `GET /v1/views` 목록 순서가 Notion 탭 순서와 달랐다(테스트 DB에서
  "완료함"이 "할 일"보다 먼저 옴). 그래서 마지막으로 연 뷰 → 체크 가능하고 미완료를 보여주는 뷰 순으로 고른다.
- **완료로 거르지 않는 뷰는 체크해도 항목이 남는다.** "내 작업"·"오늘"처럼 필터에 완료 조건이 없는 뷰는
  Notion에서도 체크한 항목이 남는다. 그대로 따르되 취소선과 함께 아래로 내린다(`ResolvedView.filtersByCompletion`).
- **속성 ID는 디코딩해서 비교한다.** 스키마는 `%3BQFf`, 뷰 필터는 `;QFf`로 같은 속성을 다르게 준다.
- **토큰 갱신은 프로세스 간 경쟁을 전제로 한다.** 실제 Notion에서 갱신하면 refresh 토큰이 바뀌고 이전 access
  토큰은 즉시 401이 된다. 앱이 갱신하면 위젯 요청이 실패하므로, 401을 받으면 먼저 Keychain을 다시 읽어 다른
  프로세스가 이미 바꾼 토큰이 있으면 그것을 쓴다(`AuthSession.refresh`).
- ~~**리스트 순서 바꾸기는 하지 않는다.**~~ Notion API에 뷰의 수동 정렬 순서를 쓰는 방법이 없다.
  → 2026-11-11: Notion에 쓰지 않고 기기에만 저장하는 순서·섹션을 넣었다 (위 결정).
- **개발 토큰은 Keychain을 쓰지 않는다.** 서명이 바뀐 개발 빌드가 macOS 로그인 키체인을 읽으면 허용 창이 떠서
  앱이 멈췄다. 디버그 빌드에서 `NT_DEV_TOKEN`이 있으면 메모리 저장소를 쓴다.
- **체크가 실패해도 되돌리지 않는다.** 잠금화면·오프라인에서 한 체크는 대기(흐린 원)로 남아 다시 보내진다.
  되돌릴 수 없는 오류로 세 번 실패하면 버리고 다음 조회에서 Notion 상태로 돌아간다 (PLAN 4.5의 "되돌리고 오류 배지" 대신).
- **앱은 캐시로 먼저 연다.** 시작할 때 Notion 응답(2~7초)을 기다리던 스피너를 없앴다. 응답이 오면 덮는다.
- **오프라인으로 추가한 항목은 뷰 조건대로 보인다.** "완료함"처럼 체크된 항목을 보여주는 뷰에서는 체크된 채로
  대기한다 (그대로 두면 뷰 필터에 걸려 사라졌다).

## 2026-11-09 — 뷰 정의를 읽어 data source 쿼리 1회로 조회한다

**근거 (`scripts/probe-views.mjs` 실측, OAuth 토큰):**

- 뷰 쿼리 결과는 페이지 ID만 줘서 항목 N개면 요청이 N+1회다. data source 쿼리는 같은 필터
  (`"me"`·`"today"` 포함)를 받고 속성까지 한 번에 준다.
- 완료 속성 추론도 `filter`와 `quick_filters`를 모두 봐야 한다.

## 2026-11-08 — 중계 서버는 loopback 바인딩 + 인증 프록시로만 노출 (2단계 적용, webhook 예외 추가)

**결정:** 중계 API는 `127.0.0.1`에 바인딩하고, 외부 접근은 인증이 걸린 리버스 프록시

**예외 — webhook 경로:** Notion이 호출하는 webhook 엔드포인트는 공개 인터넷에서 도달 가능해야

webhook 경로 하나만 공개로 열고, 그 경로는 `X-Notion-Signature` HMAC 검증
(`NOTION_WEBHOOK_SECRET`)으로 인증한다. 서명 검증 실패 요청은 본문 처리 전에 거부한다.

**근거:** Notion 인티그레이션 토큰을 보유한 프로세스다. 공개 인터넷에 직접 바인딩하면
토큰 권한 범위 전체가 노출면이 된다.
