## 2026-11-09 — 최소 OS는 iOS·iPadOS·macOS 26

**결정:** 배포 하한을 iOS 26 / iPadOS 26 / macOS 26으로 한다. 27 전용 기능(`systemExtraLargePortrait`,
리스트 `reorderable`)은 `#available`로만 켠다.

**근거:** Liquid Glass와 위젯 tinted/clear 외형이 26에서 시작한다. 하한을 맞추면 디자인을 한 벌로 유지하고
구버전 분기 코드가 없다.

## 2026-11-09 — 잠금 상태에서도 위젯 체크를 허용한다 (체크만)

**결정:** 완료 토글 인텐트(`ToggleTodoIntent`)만 `authenticationPolicy = .alwaysAllowed`로 둬서 잠금
해제 없이 잠금화면·StandBy 위젯에서 체크할 수 있게 한다. 추가·삭제·수정·뷰 변경은 잠금 해제를 요구한다.
토큰은 Keychain `AfterFirstUnlock`, App Group 캐시·대기열은 `completeUntilFirstUserAuthentication` 보호 등급.

**근거:** 잠금화면에 항상 떠 있는 메모를 보고 바로 지우는 것이 이 앱의 핵심 경험이다. 체크는 되돌릴 수
있는(다시 체크 해제) 가벼운 쓰기라 잠금 중 허용해도 위험이 작고, 내용을 바꾸거나 지우는 동작은 막는다.

## 2026-11-09 — 뷰 정의를 읽어 data source 쿼리 1회로 조회한다

**결정:** 위젯은 뷰 쿼리(`/views/{id}/queries`)를 쓰지 않는다. 뷰 정의(`GET /v1/views/{id}`)를
읽어 `filter`와 `quick_filters`를 AND로 합치고 `sorts`와 함께 `POST /v1/data_sources/{id}/query`로
보낸다. 뷰 정의는 캐시하고, 위젯 갱신마다 data source 쿼리 1회만 보낸다.

**근거 (`scripts/probe-views.mjs` 실측, OAuth 토큰):**
- Notion UI에서 만든 필터는 `filter`가 아닌 `quick_filters`에 저장됐다.
- `"me"`는 로그인 사용자로, `"today"`는 오늘 날짜로 해석되어 기대한 항목만 걸렸다. 뷰 기반 설계의
  전제가 성립한다. "today"는 상대값으로 저장되므로 날짜가 바뀌면 Notion이 다시 계산한다.
- 뷰 쿼리 결과는 페이지 ID만 줘서 항목 N개면 요청이 N+1회다. data source 쿼리는 같은 필터
  (`"me"`·`"today"` 포함)를 받고 속성까지 한 번에 준다.
- 완료 속성 추론도 `filter`와 `quick_filters`를 모두 봐야 한다.

## 2026-11-08 — 속성 매핑 대신 Notion 뷰 기반 위젯 + OAuth 로그인

**결정:**
1. 앱은 속성 매핑(제목·완료·기한 지정)을 받지 않는다. 각 위젯은 사용자가 Notion에 이미 만든 **뷰**
   하나를 Views API(`/v1/views`)로 조회해, 저장된 필터·정렬대로 보여준다. 뷰 선택은 위젯 설정
   (AppIntent 설정형 위젯)으로 받는다.
2. 완료 토글 대상은 뷰 필터가 참조하는 status/checkbox 속성으로 추론한다. Status는 Complete 그룹의
   첫 옵션으로 바꾼다. 제목은 title 속성, 기한은 뷰 정렬·필터의 date 속성으로 정한다.
3. 로그인은 Notion OAuth(public integration)를 기본으로 한다. client secret은 무상태 서버리스
   토큰 교환 함수(`auth/`)에만 둔다. internal integration 토큰 직접 입력은 직접 빌드용 대체 경로로 남긴다.

**근거:**
- 속성 지정 화면 자체가 허들이다. 사용자는 Notion에서 "오늘", "내 작업" 같은 뷰로 이미 의도를
  표현해 두었으므로, 그 뷰를 그대로 쓰면 지정할 것이 거의 없다.
- "작업 데이터베이스로 지정"(Turn into Tasks)은 API에 노출되지 않아 쓸 수 없다. 뷰가 API로 읽을 수
  있는 사실상 유일한 사용자 의도다.
- Status 그룹은 To-do / In progress / Complete로 고정이라 "완료"의 의미가 모호하지 않다.
- 진짜 큰 허들은 인티그레이션 생성·토큰 복사·DB 공유다. OAuth 페이지 선택 화면이 이를 한 번에 처리한다.
- Notion OAuth는 코드 교환과 토큰 갱신 모두 client secret을 요구하고 PKCE가 문서에 없다. secret을
  앱 번들에 넣으면 추출되어 앱 사칭이 가능하므로 함수가 필요하다. 함수는 데이터를 저장·조회하지 않고,
  호출이 로그인·갱신 때뿐이라 서버리스 무료 티어로 충분하다. "서버 없음" 원칙은 "데이터 서버 없음"으로 바뀐다.

**미확인 (구현 전 실제 API로 검증):**
- 뷰 필터의 `"me"`가 OAuth 토큰에서 로그인 사용자로 해석되는지. internal integration 토큰에서는
  봇으로 해석되어 "내 작업" 뷰가 비어 보일 가능성이 있다.
- "오늘" 같은 상대 날짜 필터가 쿼리 시점마다 다시 계산되는지.

## 2026-11-08 — 중계 서버는 2단계 옵션으로 미룬다 (「중계 서버를 먼저 세운다」 대체)

**결정:** 1단계는 서버 없이 앱·위젯이 Notion API를 직접 호출한다. 중계 서버는 위젯 반영
지연(15~60분)이 실제로 불편할 때 2단계로 추가하며, 역할은 "Notion webhook 수신 → APNs 푸시
발송"으로 한정한다. 데이터 조회·토글은 2단계에서도 클라이언트가 Notion과 직접 주고받는다.

**근거:** 「서버 먼저」의 전제였던 A/B 미정 상태가 해소됐다(아래 경로 B 확정). 남은 근거를
1인·2기기 기준으로 다시 보면:
- 레이트리밋(평균 3 req/s): 위젯 갱신 15~60분 간격 + 앱 조회 수준이면 여유가 크다.
- 토큰 보관: 본인 전용 앱이면 App Group 공유 Keychain으로 충분하다.
- 서버가 없으면 불가능한 것은 **위젯 즉시 갱신** 하나뿐이다. webhook은 공개 HTTPS로만
  받을 수 있고, APNs 푸시도 서버에서만 보낼 수 있다.

서버를 먼저 만들면 운영·외부 노출 부담을 지면서 1단계에서는 얻는 것이 없다.

**재검토 조건:** 사용자·기기가 늘거나 앱을 배포하게 되면 서버 캐시·토큰 서버 보관을 다시 검토한다.

## 2026-11-08 — ~~중계 서버를 먼저 세운다~~ (대체됨)

> 위 「중계 서버는 2단계 옵션으로 미룬다」로 대체됨. A/B 미정이 전제였으나 B로 확정됐다.

**결정:** 클라이언트 경로(A/B)를 확정하기 전에 셀프호스팅 중계 API를 먼저 만든다.

**근거:** 위젯 쪽 제약(Apple 빌드 환경·서명 계정·WidgetKit 갱신 예산)은 클라이언트 레이어에만
걸린다. 서버는 A·B 어느 쪽에서도 그대로 쓰이므로 선택을 미뤄도 작업이 낭비되지 않는다.
반대로 클라이언트를 먼저 만들면 Notion 레이트리밋을 직접 맞는 구조가 되어 재작업이 생긴다.

## 2026-11-08 — Notion webhook + 폴링 백업 병행 (2단계 적용)

**결정:** `data_source.content_updated` webhook을 1차 신호로 쓰고, 저빈도 폴링을 백업으로 둔다.
2단계 중계 서버를 도입할 때 적용한다. 1단계에서는 위젯 타임라인 갱신이 폴링 역할을 한다.

**근거:** webhook은 이벤트가 집계(aggregate)되어 들어오고 페이로드가 메타데이터뿐이라
유실·누락 시 상태가 조용히 어긋난다. 폴링 백업이 있으면 최악의 경우에도 수렴한다.

## 2026-11-08 — 중계 서버는 loopback 바인딩 + 인증 프록시로만 노출 (2단계 적용, webhook 예외 추가)

**결정:** 중계 API는 `127.0.0.1`에 바인딩하고, 외부 접근은 인증이 걸린 리버스 프록시
(또는 사설 네트워크 터널)를 통해서만 허용한다. 클라이언트는 API 키를 제시한다.

**예외 — webhook 경로:** Notion이 호출하는 webhook 엔드포인트는 공개 인터넷에서 도달 가능해야
하므로 사설 터널 뒤에 둘 수 없고, Notion은 클라이언트 API 키를 제시하지 않는다. 프록시에서
webhook 경로 하나만 공개로 열고, 그 경로는 `X-Notion-Signature` HMAC 검증
(`NOTION_WEBHOOK_SECRET`)으로 인증한다. 서명 검증 실패 요청은 본문 처리 전에 거부한다.

**근거:** Notion 인티그레이션 토큰을 보유한 프로세스다. 공개 인터넷에 직접 바인딩하면
토큰 권한 범위 전체가 노출면이 된다.
